### AI Playtesting Bot

The bot (`js/bot.js`) takes over full player control — movement, proposals, and upgrades — to stress-test game balance across arbitrarily many cycles without manual play. It hooks into Phaser's `postupdate` event, overrides `px`/`py` each frame, and reuses the scene's existing `_pathCrossesRing` / `_orbitRing` helpers for navigation.

**Console API**

| Command | Effect |
|---------|--------|
| `_bot.start()` | Bot takes over; keyboard suppressed |
| `_bot.stop()` | Restore keyboard control |
| `_bot.stats()` | Print cycle metrics as a console table |
| `_bot.speed(n)` | Set `devTickMult` (requires `?dev`) |

**In-cycle priority order** (re-evaluated every 250 ms):

1. Collect finished measurement results from the control room
2. Stay in the control room while a measurement is running (proximity-gated timer)
3. Start a deposited-but-unstarted measurement
4. Stay near the hutch while experiment setup is in progress
5. Trigger experiment setup at the correct beamline hutch
6. Pick up finished prep samples from the prep table
7. Deposit raw samples at the matching lab-type prep table (waits nearby if full)
8. Collect raw samples from NPCs — sorted by urgency (leave time < 20 s first), then by dominant lab type in hand for batching; throttled to at most 2 NPCs active at once to prevent departure pile-ups

**Proposal selection** (automated at cycle start):

Scores each proposal by `rep − samples × 1.5`, adds a diversity bonus for the first proposal on each beamline, caps at 2 per beamline, and selects the top `5 + postdocs` proposals. This balances throughput against rep density.

**Between-cycle automation** (CycleEndScene):

- Upgrades bought in priority order: extra NPC slot → prep capacity → NPC positioning → measurement speed (per beamline) → prep speed → ring maintenance.
- Action chosen: train the lowest-level postdoc; fall back to publishing a paper.
- Continues to the next proposal screen automatically.

**Design use**: watch the overlay label during a cycle. Sustained `wait meas` / `start meas` time indicates the measurement phase is the throughput bottleneck. Sustained `wait wet` / `wait dry` indicates prep capacity is the bottleneck. The `npc: N` counter in the overlay shows how many NPCs are currently waiting; if it often reads 2 the throttle is active and NPC arrival rate is healthy.

### RL Training Environment (`rl/`)

A headless, versioned Python simulation used to train and evaluate reinforcement learning agents against the hand-coded bot. It approximates the browser mechanics; policies must be validated in the browser because differences in movement, timing, and interactions can create a simulation-to-game transfer gap.

**Files**

| File | Purpose |
|------|---------|
| `rl/facility_env.py` | `gymnasium.Env` implementation of the 180-second game cycle |
| `rl/train.py` | BC pre-training + PPO fine-tuning pipeline |
| `rl/requirements.txt` | `gymnasium`, `stable-baselines3`, `numpy` |

**Simulation design**

- **Action space**: `Discrete(16)` — navigate to one of 15 named locations (2 prep tables, 4 × hutch+ctrl, 5 NPC slots) or wait in place.
- **Observation**: 145-dim float32 vector under the default v2 configuration, encoding time remaining, current location (one-hot), held items, prep and measurement states, experiment setup, NPC urgency and proposal value, hazards, upgrades, reputation, and progression.
- **Simulation model**: event-driven (jumps to the next relevant timer expiry rather than ticking at 60 fps) — runs at ~70,000 steps/sec in pure Python.
- **Travel times**: pre-computed angular arc distances on the ring corridor, with room-entry overhead for beamline hutches/ctrl rooms.
- **NPC departure**: mirrors the game formula exactly (`leave_ms = Σ(prep + setup + meas) × 2.5 × 1000`; penalty = `max(1, round(lost/total × rep × 0.5))`).

**Training pipeline**

1. **Behavioural cloning** (BC): collect 2,000 heuristic episodes (~100 k state–action pairs), normalise observations using the training env's running statistics, and minimise cross-entropy between the policy network's output and the heuristic labels (30 epochs). This gives the RL agent a strong starting policy for free.
2. **PPO fine-tuning**: 500 k steps with `n_envs=4`, `n_steps=2048`, `net_arch=[256,256]`, `ent_coef=0.01`. Intermediate shaping rewards (+20% of per-sample rep at raw pickup, prep completion, and exp-setup completion) keep the gradient signal dense.

**Historical benchmark results** (legacy v1 rules; 200 evaluation episodes each)

| Agent | Rep/cycle | Samples/cycle |
|-------|-----------|---------------|
| Hand-coded heuristic bot | 41 ± 20 | 4.9 |
| Pure PPO (1 M steps, no BC) | 29 ± 24 | 2.0 |
| **BC + PPO (500 k steps)** | **62 ± 21** | **6.1** |

The historical BC+PPO agent was ~50% more efficient than the historical hand-coded bot. These figures are not comparable with the corrected v2 rules and observation model; new agents must be trained and evaluated on identical v2 seeds before making current balance claims.

### AI Technology Decision: First-Party RL vs Jev

**Decision:** use a first-party reinforcement learning policy as the primary route for automated moment-to-moment gameplay. Keep the deterministic heuristic as the baseline and runtime fallback. Use TypeSafe AI's hosted Jev decision model only as an optional development, strategic-decision, and playtesting tool; do not make it a required dependency of the shipped game.

| Responsibility | Preferred system | Rationale |
|---|---|---|
| In-cycle movement, timing, inventory, and station routing | First-party RL | Learns directly from the game's reward, runs locally with low latency, works offline, and has no per-action API cost. |
| Reliable baseline and failure fallback | Hand-coded heuristic | Deterministic, inspectable, inexpensive, and stable across service outages or model changes. |
| Proposal admission and upgrade experiments | Jev, evaluated experimentally | These are bounded contextual choices that match Jev's typed `Choice` interface and do not require frame-level control. |
| Alternative play styles and balance testing | Jev or separately trained RL personas | Useful for discovering bottlenecks and strategies not represented by the main policy. |
| Shipping player or postdoc AI | Local rules/RL | Avoids requiring a protected server-side API key, network connectivity, ongoing inference cost, and tolerance for external latency or outages. |

**Why RL is the primary investment**

- The project already has the costly foundations: a Gymnasium environment, deterministic seeds, reward and outcome metrics, heuristic demonstrations, PPO training, and paired evaluation.
- The gameplay loop is a repeated optimization problem with measurable outcomes. RL can train against reputation, sample completion, loss, travel, and waiting time rather than relying on a general model's immediate judgment.
- A trained policy can execute locally and cheaply at gameplay frequency. Jev is a hosted, reactive decision service and does not provide the same native long-horizon optimization.

**Jev development experiment**

`rl/jev_play.py` serializes the simulation into semantic state and asks Jev to choose among the same 16 high-level actions used by the RL environment. It caches repeated wait decisions, records latency/token/confidence data, falls back to the heuristic on low confidence or API errors, and compares both policies on identical seeds. This full-game controller is a benchmark, not the intended production architecture.

Jev earns a continuing place in the workflow only if controlled experiments show that it does at least one of the following:

1. Improves proposal or upgrade decisions over the heuristic on held-out seeds.
2. Finds reproducible strategies or balance problems that the heuristic and trained RL policy miss.
3. Provides useful uncertainty signals that identify ambiguous game states or unclear player choices.

**Transfer requirement:** an RL score in the Python simulation is not sufficient for production. Candidate policies must be replayed against equivalent browser scenarios and checked for exploitative behavior caused by simulator simplifications. If transfer error is material, increase simulator fidelity or train through a browser/game-engine adapter before integration.
